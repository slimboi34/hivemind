# How Hivemind creates its agents, and what to rebuild

Status: review and plan, 18 November 2026. Section 3 lists what was fixed alongside this note.
Everything else is proposed, not built.

Scope: how a question and its evidence become a cast of simulated participants, how those
participants are run, and how the system around them is put together. How information then
spreads between agents is covered separately in
[INFORMATION_DYNAMICS.md](./INFORMATION_DYNAMICS.md); this note does not repeat it.

Evidence: the code at `dd6ec98`, and the two stored runs `sim_168d7ecb477b` (74 agents) and
`sim_8dd3a542e55c` (78 agents), both on the Nvidia CEO scenario.

---

## 0. Summary

The engine inherited from MiroFish casts one agent for every named thing in the knowledge
graph and hands each a long written persona. That is the whole population model. It has three
consequences that matter more than anything else here:

1. **There is no public.** Both stored runs have zero ordinary people. "Nvidia shareholders"
   is one account. A product that forecasts public reaction is simulating a room of
   spokespeople.
2. **Most of what is configured per agent is never used.** Stance, sentiment bias, influence
   weight, posting rates and response delays are generated by the model, saved, and never
   read by the runner. Only `activity_level` and `active_hours` affect a run.
3. **The cast was partly miscast.** In the stored runs 88% and 96% of agents were written as
   faceless institutions, including Ron Wyden, Tim Cook and Jensen Huang, and opening posts
   were handed to the wrong accounts. These were bugs, and they are fixed (Section 3).

The system around the agents is a browser-driven wizard over a Flask app that keeps job state
in memory, starts the simulation as a subprocess, and talks to it through files. It works for
one user on one machine. It cannot run unattended, resume after a restart, or run the same
question several times, which is what both ease of use and accuracy need next.

**Recommended order of work**

| # | Work | Why first | Size |
|---|---|---|---|
| 1 | One run engine: a single job that takes a question to a briefing, with saved state | Unlocks one-click runs, resuming, and repeated runs | M |
| 2 | A cast plan: choose who is in the run, and add a sampled public | Fixes "no public", the largest gap in what the product claims | M |
| 3 | Structured agent state that the runner uses (stance, salience, relationships) | Makes configured behaviour real and measurable | M |
| 4 | Repeated runs with a fixed seed per run | Turns one anecdote into a result with a spread | S after 1 |
| 5 | Local graph store in place of Zep Cloud | Removes the one hard external service | L |

Items 2 to 4 change what Hivemind predicts. They need the backtest gate described in
INFORMATION_DYNAMICS.md Section 5 before any claim that they are more accurate.

## 1. How an agent is created today

| Step | What happens | Where |
|---|---|---|
| 1. Ontology | The model reads the evidence and the question and designs about ten entity types for this project, such as `GovernmentOfficial` or `InvestmentAnalystFirm`. | `ontology_generator.py` |
| 2. Graph | Zep Cloud extracts entities and relationships from the text. | `graph_builder.py` |
| 3. Cast | Every graph node carrying one of the designed types becomes an agent. Nothing is filtered, ranked or merged. | `zep_entity_reader.py:221` |
| 4. Persona | One model call per agent writes a bio and a persona of about 700 words, from the node summary and two Zep searches. Three in parallel. | `oasis_profile_generator.py:274` |
| 5. Behaviour | Agents are sent to the model fifteen at a time for activity level, active hours, stance, sentiment bias, influence weight and posting rates. | `simulation_config_generator.py:844` |
| 6. Opening posts | One call writes the opening posts and names who posts each. | `simulation_config_generator.py:651` |
| 7. Files | Personas are written as a CSV for one platform and JSON for the other; everything else goes in `simulation_config.json`. | `simulation_manager.py:244` |
| 8. Run | A subprocess loads the profiles into OASIS. Each round it picks active agents and gives each one model call to choose an action. | `scripts/run_parallel_simulation.py:1040` |

Preparing a 75-agent run costs about 82 model calls (75 personas, 5 behaviour batches, time
and event config) and 150 Zep searches. Running it costs one call per active agent per round
per platform, and every one of those calls carries that agent's full persona.

## 2. What is wrong with it

### 2.1 Who gets cast

- **No selection.** A node is an agent if it has a type. The stored runs cast "Jensen Huang's
  wife", "US intelligence" and "Nvidia vice president" as posting accounts because the
  documents mention them. There is no test for whether an entity would plausibly speak.
- **No public.** The cast is whoever the evidence names, so it is elites and institutions.
  Nobody represents customers, employees, voters or retail investors except as a single
  account with a collective name.
- **No size control.** Cast size is the number of matching nodes. A short memo gives a dozen
  agents; a long report gives hundreds, with cost to match.
- **Duplicates.** Graph extraction can produce "House committees", "Congress" and "US House of
  Representatives" as three accounts. Nothing merges them.

### 2.2 How personas are written

- **Person or organisation was decided by a fixed list** of ten type names from upstream's
  university example (`student`, `professor`, ...). Project-specific types never matched, so
  almost everyone got the institution prompt: age 30, gender "other", an "official account"
  voice. Measured: 65 of 74 and 75 of 78 agents. *Fixed.*
- **Fenced JSON lost fields.** When the model wrapped its reply in a code fence, parsing
  failed and a salvage path kept only the bio and persona text, dropping age, gender, country,
  profession and interests without an error. *Fixed.*
- **Country was requested in Chinese** whatever the run's language; the stored English runs
  have 41 and 45 agents with `美国`. *Fixed.*
- **Personas are prose only.** Position, relationships and what the agent already did are
  buried in 700 words. Nothing downstream can read them, compare them or check them.
- **Context is thin and generic.** Every agent's Zep search uses the same query template, and
  the context is cut at 3,000 characters.
- **Invented statistics.** Follower counts, karma and post counts are random numbers.

### 2.3 How behaviour is configured

- **Dead fields.** `stance`, `sentiment_bias`, `influence_weight`, `posts_per_hour`,
  `comments_per_hour`, `response_delay_min/max`, `hot_topics` and `narrative_direction` are
  generated and stored, and the runner reads none of them. The briefing now shows `stance` as
  background, which is its first use anywhere.
- **Activation is two dice rolls.** An agent is a candidate if the hour is in its
  `active_hours` and a random draw is under its `activity_level`; the round then samples a
  random number of candidates. Nothing an agent has seen affects whether it acts.
- **The prompts carry upstream's example.** The behaviour prompt still describes universities,
  students and "Chinese daily routines" as its reference case.

### 2.4 How opening posts are assigned

- **By type, not by name.** The model chose a poster *type* per post and the code handed posts
  out in turn to accounts of that type. In `sim_168d7ecb477b` a post beginning "Senator Ron
  Wyden and Representative Richard Neal are opening a probe" went to Chuck Schumer, and "Trump
  says Huang told him..." went to Ron Wyden. Those posts open the run and are the most
  reacted-to content in it. *Fixed.*
- **Still open:** opening posts are keyed by agent in the runner, so two posts for one account
  would silently drop the first while both are logged.

### 2.5 How agents are run

- **No relationships.** Both runs have zero follow edges. The knowledge graph holds who
  regulates, funds, competes with and covers whom, and none of it reaches the simulated
  platforms.
- **One model for everyone.** The crowd and the key actors use the same model at the same
  cost. A second "boost" endpoint exists only to spread load.
- **Nothing is seeded.** Usernames, activation and sampling use the global random generator,
  so no run can be reproduced or compared like for like.
- **Four copies of the loop.** The Twitter and Reddit loops in `run_parallel_simulation.py`
  are near-duplicates, and `run_twitter_simulation.py` and `run_reddit_simulation.py`
  duplicate them again (about 3,200 lines for one loop).

## 3. Fixed with this note

| Fix | Effect on new runs | Where |
|---|---|---|
| Person or organisation is read from the type's head noun (`GovernmentOfficial` is a person, `GovernmentAgency` is not), and the person prompt lets the model fall back to an organisation account when the entity is really a firm or a crowd | Named people get a human persona with a real age and gender | `oasis_profile_generator.py` |
| Code fences are stripped before persona and config JSON is parsed | No more silently dropped persona fields | both generators |
| Country follows the run's language | No mixed-language profile fields | `oasis_profile_generator.py` |
| Opening posts name their poster from the full cast list, are written in that account's own voice, and are matched by name before type | Opening posts come from the account that would post them | `simulation_config_generator.py` |

These are correctness fixes, but they do change the input to new runs, so new runs will not
match old ones. The two stored runs are unchanged. Checked by unit tests
(`tests/test_agent_casting.py`) and by generating personas for two entities against the live
model; no full simulation has been run with them yet.

## 4. A better way to create agents

### 4.1 A cast plan (changes predictions)

Insert one step between the graph and the personas that decides who is in the run and writes
it down as `cast.json`, which the user can read and edit before spending money.

- **Score every entity for voice:** would this entity post about this question? Drop the ones
  that would not (a spouse, an unnamed vice president), and merge duplicates.
- **Set a budget:** the user picks a cast size (say 30, 75 or 200) and the plan fills it by
  score, so cost is chosen up front.
- **Add a sampled public.** For each affected group the question implies (customers, staff,
  retail investors, voters), generate a set of ordinary people whose attributes are drawn from
  stated distributions: age, region, how much they care, how they lean. One named institution
  is one account; one public group is many accounts with spread. This is the single largest
  change to what the product can claim.
- **Tier the cast.** Key actors get a full persona and the strong model. The public gets a
  short persona from a template plus sampled attributes, and the cheap model. This cuts
  preparation cost and makes larger casts affordable.

### 4.2 Structured agent state (changes predictions)

Replace "everything is prose" with a small record per agent, kept beside the persona:

```
{ "kind": "person | organisation | public",
  "stance": -1..1, "salience": 0..1, "confidence": 0..1,
  "goals": ["..."], "red_lines": ["..."],
  "relationships": [{"to": "Commerce Department", "type": "oversees", "valence": -0.4}],
  "facts_known": ["..."] }
```

- The persona is generated from this record, so the two cannot disagree.
- The runner reads it: salience drives activation, relationships seed the follow graph, and
  stance can be re-measured after each round to give a trajectory.
- Remove or wire every dead field. A field that is generated must be used or deleted.
- Relationships come straight from knowledge-graph edges, which exist today and are thrown
  away at this step.

### 4.3 Cheaper and reproducible runs

- **Seed everything** from one run seed stored in the config.
- **Shorten what is sent each turn.** Send a compact persona card on every call and keep the
  full persona for interviews. With prompt caching on the stable part, the per-turn cost of a
  700-word persona falls sharply.
- **One loop.** Collapse the four runner copies into one platform-parameterised loop.

## 5. The system around the agents

### 5.1 Today

| Part | How it works | Limit |
|---|---|---|
| Orchestration | The browser calls each of five stages in turn and polls | Closing the tab stops the pipeline; nothing can run unattended |
| Job state | `TaskManager` keeps tasks in memory; background work runs in daemon threads | A backend restart loses every running job |
| Simulation | A subprocess per run; the backend reads its JSONL logs and sqlite files | No resume; a crash leaves a half run |
| Interviews | Commands and replies are JSON files in `ipc_commands/` and `ipc_responses/`, polled | Slow, and the process must be kept alive after the run |
| Knowledge graph | Zep Cloud, for extraction, search and agent memory | Hard external dependency, rate limits, data leaves the machine |
| Storage | JSON, CSV, JSONL and sqlite files under `uploads/` | No index across runs; history is a directory scan |
| Model access | Three separate call paths (LLMClient, raw OpenAI client in the generators, CAMEL in the runner) | JSON handling, retries and cost tracking differ in each; the fence bug lived in one of them |
| Configuration | One large JSON written by the model, partly unused | No schema, no validation |

### 5.2 Target

- **A run engine.** One backend job owns a run from question to briefing as a state machine
  (`brief → graph → cast → personas → simulate → briefing`), with every stage's inputs and
  outputs saved, so a run can resume from the last finished stage. The five-step screen
  becomes a view of that job. This is the prerequisite for the one-click run.
- **A run store.** One sqlite database for projects, runs, stages, casts and costs. The
  per-run action logs stay as files.
- **One model gateway.** Every call goes through one client that strips fences, validates
  against a schema, retries, records tokens and cost per stage, and picks the model by tier.
- **A typed config.** `simulation_config.json` gets a schema; unknown or unused fields fail
  a test instead of sitting in the file.
- **Runs as a set.** The engine runs the same cast N times with different seeds and the
  briefing reports what holds across runs. Consensus across runs is stronger evidence than
  consensus within one.
- **A graph store interface.** Put Zep behind `GraphStore` (extract, search, neighbours,
  write memory), then add a local implementation. Hivemind then runs on a model key alone.
- **Interviews without the live process.** Rebuild an agent from its persona, state and
  action history on demand, so the simulation process can exit when the run ends.

### 5.3 Order and risk

1. **Run engine and run store.** No change to predictions. Everything else builds on it.
2. **Model gateway and typed config.** No change to predictions; removes a class of silent
   failures.
3. **Cast plan with tiers and a sampled public.** Changes predictions. Ship behind a setting,
   compare old and new casts on the same question, and backtest.
4. **Structured state wired into the runner.** Changes predictions. Same gate.
5. **Repeated seeded runs.** Multiplies cost by N; pair with tiering.
6. **Local graph store.** Large; do it last, behind the interface.
